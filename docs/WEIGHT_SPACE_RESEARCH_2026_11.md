# Weight-space programming and the ABI roadmap

Reviewed 2026-11-10. This is a research positioning note, not new experimental
evidence or a claim that ABI is novel, superior, production-complete or obsolete.

## What the cited work demonstrates

Takehi, Teoh, Zhang and Khattab report direct weight inspection, small-network
construction and targeted behavioral repair. On Qwen3.5-0.8B, their loop-removal
edit changes 131,072 weights; reported MATH-500 accuracy rises from 7.9% to 48.1%
with a 50-batch evaluation budget. Their non-looping Gemma 3 270M experiment
does not establish a math improvement. This distinguishes recovering obstructed
behavior from adding a missing capability. These are the authors' reported
results; we have not reproduced them. The demonstrations do not establish
arbitrary English capability transplantation or independent portable artifacts.
Source: [Sparks of Weight-Space Programming, November 2, 2026](https://rikiyat.github.io/blog/weight-space-programming/).

## Implication for this project

Our inference is that direct weight editing is a serious candidate acquisition
baseline, not a reason to discard evidence-bound packaging and host conformance.
That does NOT insulate ABI from competition: a simpler patch can make an ABI
mechanism unnecessary if it achieves the same capability and deployment contract
more cheaply. There is no measured ABI advantage over this new method here.

ABI's immediate bottleneck remains a qualified, generalizable English acquisition
result. R97's nonce reasoning, R7's conformance release and newer English diagnostics
are different lineages. A small successful reasoning package cannot substitute
for an English-core qualification. R103 failed before recipient comparison.
R104 first validates finite evaluator obligations and then tests a qualified
control/recipient boundary; it does not add another acquisition backend.

LayerCake owns host execution and package lifecycle, not this acquisition study.
No LayerCake package role, sealed host or performance claim changes here. A
base-bound tensor patch would require its own compatibility and mutation contract;
it cannot be advertised as cross-architecture portability or silently treated as
an existing immutable cake. Installation and active execution must preserve the
applicable host's integrity and isolation requirements.

## Candidate future comparison, not an executed result

After a reliable task/control boundary exists, preregister two separate questions:
repair of a measured existing failure, and acquisition of a genuinely new bounded
capability. Compare direct weight editing, ordinary LoRA, sequence distillation
and the specific ABI mechanism, with the same pinned target, task information,
off-task regressions, unseen holdout and quality gates. Account for editor/source
inference, all proposals and evaluations (including failures), imported data,
tensor edits, final artifact bytes, training cost, inference time and memory.
Do not equate sparse changed weights with physically sparse execution.

Require causal ablations, source-free execution, reproducibility and exact base
hashes for coordinate-bound edits. Make any cross-host claim earn separate host
tests. Favor whichever method meets the actual product contract; do not relabel
ordinary editing or distillation as an ABI invention. No editor API spending,
weight-editing campaign or new host integration is launched by this note.

The moonshot remains `FULL_MOONSHOT_NOT_PROVEN`. Human quality, independent
hardware, broad-English acquisition, capability isolation and minimization remain
open. The peer review's static inspection is helpful, not independent execution
of our scientific campaign.
